# 多 Agent 协作开发

本 Skill 负责执行流程；项目约束和模式定义见根目录 [AGENTS.md](../../../AGENTS.md)。主 Agent 始终承担最终责任，技能文件本身不会创建子 Agent 能力。

## 1. 决定执行方式

- 读取用户指定模式；未指定时使用 AUTO。遵守 AGENTS.md 中的委派条件和并发上限。
- 核对真实的创建、消息、状态与结果回收工具，以及当前工作区是共享还是隔离。工具存在不代表已经执行成功。
- 先简要说明任务划分与依赖，再调用工具；用户已经授权的正常委派不需要逐个确认。
- 工具不可用时按阶段完成可执行部分，并说明限制。需要时提供独立 Cloud 任务提示词，明确它们尚未启动。
- 简单任务不为填满角色而增加 Agent。可以只委派一个有独立价值的研究、实现或审查任务。

## 2. 角色与权限

| 角色 | 工作与交付 | 默认写入权限 |
| --- | --- | --- |
| Explorer | 结构、关键路径、影响范围与未知项 | 不修改项目文件 |
| Researcher | 官方资料、适用版本、证据与限制 | 不修改项目文件 |
| Architect | 模块边界、接口、依赖和方案取舍 | 不修改项目文件；主 Agent 决定方案 |
| Developer | 分配范围内的实现、必要测试与变更说明 | 仅分配的文件或目录 |
| Tester | 实际测试、复现步骤和结果 | 不修改源代码或测试基线 |
| Reviewer | 针对指定版本的差异审查，按严重程度报告问题 | 不修改项目文件 |

“只读”角色可以运行获准的验证命令，产生隔离的缓存、日志或报告；不得借验证修改受版本控制的文件、更新快照、自动格式化或安装依赖。需要这些修改时，由主 Agent 分配写入范围。测试输出目录、端口和共享服务也要避免冲突。

## 3. 委派任务单

每个子任务至少明确以下信息；可以直接写在委派消息中：

```text
任务 ID / 角色：
目标与不包含的内容：
输入：仓库、cwd、基线提交、相关文档与接口
前置依赖：已满足的输入；尚未满足则不得开始依赖它的工作
权限：只读，或允许写入的具体文件/目录
共享文件负责人：
交付物：结论/修改列表/补丁或提交、证据、未完成项
验收：具体行为、检查方式与通过条件
反馈条件：接口不满足、需越界写入、需求冲突或验证受阻时先反馈
再委派：默认禁止；允许时写明子任务和剩余并发预算
```

按任务提供足够上下文，不要求子 Agent 猜测用户意图。不把凭据或无关私有数据放入消息。

## 4. 执行与文件交接

- 先确定接口和文件所有权，再启动并行写入。存在前置依赖的工作按顺序安排；只读研究可以并行。
- 共享工作区：每个文件只有一个写入者。主 Agent 不同时修改子 Agent 拥有的文件。Git 暂存、提交、分支切换和推送默认由主 Agent 统一执行。
- 隔离工作区：记录基线与分支，通过明确提交或补丁交接；主 Agent 检查后整合，不假设对方未提交修改会自动出现。
- 交接写入权时，先确认原负责人已停止写入，检查其现有差异，再把范围交给下一位。不能仅发出中断就假定写入已结束。
- 子 Agent 汇报真实完成情况、修改路径、检查命令与结果、剩余问题。完成消息不等于验收通过。
- 主 Agent 持续处理不依赖等待结果的工作，向用户说明关键进展；用实际状态工具了解进度，避免无意义频繁轮询。

## 5. 阻断与失败处理

- 对卡住、失败或不完整的任务，先查看状态和已有证据，区分运行缓慢、输入缺失、环境错误与实现问题。
- 输入缺失时补齐上下文；任务过大时缩小范围；必要时由主 Agent 接手或重新分配。交接前遵守停止写入和差异检查规则。
- 同一错误没有新证据或条件变化时不重复执行；修正后的验证仍失败，重新诊断或报告阻断，不能无限重试。
- 结论冲突时核对原始资料、版本与复现结果，由主 Agent 决定；证据不足则保留未知，不采用多数投票。
- 子 Agent 扩大范围、改变接口或增加依赖前向主 Agent 反馈。主 Agent 在已有授权内决定，只有超出授权或关键需求缺失才询问用户。
- 未完成或未验证的项保持明确状态，不因 Agent 结束而自动标记完成。

## 6. 整合、验证与审查

1. 收齐交付物，检查实际 diff、文件所有权、接口一致性及是否混入无关变更。
2. 整合后运行与变更相关的检查；此前单个模块通过不能替代集成验证。
3. Reviewer 针对明确版本审查：记录基线提交、目标提交，或基线加完整工作区 diff（包括未跟踪交付文件）；审查期间暂停被审查文件的写入。
4. 审查报告给出问题位置、影响、证据和严重程度；无发现时说明检查范围及限制。
5. 修复确认的问题，重新执行受影响的验证。审查后新增或修改的内容需要相应复查，不能沿用旧审查结论。
6. 主 Agent 核对最终差异和验收条件，再按授权提交或交付。未通过项如实列出，不能用子 Agent 的结论代替检查。

## 7. 长任务状态与恢复

只有跨阶段、多模块或可能跨会话的长任务，才由主 Agent 在 `docs/task-state.md` 维护精简状态。不存在时按需创建，不为每个小改动新增记录。

记录：任务目标及约束、当前阶段、实际基线提交、工作区差异摘要、任务 ID 与依赖、负责人及写入范围、状态、验证证据、阻断和下一步。状态使用 pending / running / blocked / done；done 必须满足对应验收条件。关键阶段结束或交接时更新，不写入凭据。

恢复时核对实际 cwd、Git 状态、文件和工具；旧 Agent ID、服务、端口与缓存都需要重新确认。状态文档是线索，不是运行状态的保证。主 Agent 收回失效的分配并重新安排，保留用户已有修改。

## 8. 交付

简要汇总成果、真实分工、验证与限制。未创建原生子 Agent 时明确说明原因。不要把单 Agent 内部角色分析描述成多 Agent 执行，也不要把提供了独立任务提示词写成已运行任务。
