# 多 Agent 协作开发技能

## 技能目标

帮助主 Agent 以可检查、可追踪的方式完成复杂开发任务。主 Agent 始终对最终结果负责。

本技能是工作流程说明，不会凭空赋予运行环境创建子 Agent 的能力。必须先检查当前 Codex 运行环境实际提供的工具和能力。

## 一、确定执行模式

读取用户任务中的模式：

- `MODE=AUTO`：自动判断是否需要委派；默认模式。
- `MODE=MANUAL`：遵循用户指定的角色、数量、职责和顺序。
- `MODE=SINGLE`：只由主 Agent 完成，不创建子 Agent。

没有明确指定时使用 `AUTO`。

## 二、判断是否值得委派

### 不委派

适用于：
- 单文件小修改；
- 简单解释或代码问答；
- 需求明确且工作量较小的 Bug 修复；
- 子任务之间高度依赖，拆分反而增加协调成本。

### 适度委派

适用于：
- 需要先探索多个模块再实施；
- 需要同时进行技术调研和项目分析；
- 需要独立测试或审查；
- 存在可并行处理的不同模块。

建议先使用 2～3 个子 Agent。只有任务规模和运行环境确实需要时，才增加到最多 5 个。

## 三、确认运行环境能力

在创建子 Agent 前，检查当前会话是否实际提供原生 Subagents 能力，包括创建、发送任务、查看状态、接收结果等机制。

### 如果原生 Subagents 可用

- 使用当前环境实际提供的调用方式创建子 Agent。
- 不要臆造工具名称、命令或配置项。
- 等待并读取真实的执行结果。
- 向主 Agent 汇报每个 Agent 的状态、结果和未完成事项。

### 如果原生 Subagents 不可用

- 明确告诉用户当前环境不能在本任务内原生创建子 Agent。
- 不得把主 Agent 内部按角色分段思考描述成多个真实 Agent。
- 可以为用户生成独立 Cloud 任务提示词、分支分工和交接要求，让用户分别启动任务。
- 如果用户希望继续当前任务，可以由主 Agent 按阶段完成，并如实说明这是单 Agent 执行。

## 四、角色库

按任务选择角色，不必每次全部使用。

### Explorer｜项目探索员

任务：
1. 阅读项目目录和关键配置。
2. 找出相关模块、入口、调用链和现有实现。
3. 检查依赖关系和潜在影响范围。
4. 不修改文件。

交付格式：
- 项目相关结构；
- 关键文件路径；
- 当前实现摘要；
- 风险、未知事项和建议。

### Architect｜架构师

任务：
1. 分析需求和约束。
2. 设计模块边界、数据结构和接口。
3. 识别依赖、兼容性和性能风险。
4. 给出实施顺序和验收标准。
5. 默认不修改业务代码。

交付格式：
- 推荐方案及理由；
- 模块和接口设计；
- 实施步骤；
- 风险及替代方案；
- 验收标准。

### Researcher｜技术研究员

任务：
1. 调研相关框架、库、协议或工具。
2. 优先查阅官方文档和项目已有资料。
3. 标明资料时间、适用版本和限制。
4. 区分已证实事实与推测。

交付格式：
- 关键结论；
- 资料来源；
- 版本与适用条件；
- 推荐做法和注意事项。

### Developer｜开发工程师

任务：
1. 按明确范围修改代码。
2. 遵循既有架构和代码风格。
3. 为修改增加或更新必要测试。
4. 不擅自扩大修改范围。

交付格式：
- 修改文件列表；
- 主要实现说明；
- 执行过的测试和结果；
- 未完成事项。

### Tester｜测试工程师

任务：
1. 根据需求设计测试用例。
2. 执行相关测试、构建和检查。
3. 覆盖边界条件和异常流程。
4. 默认只读；如需修改测试文件，先明确授权和文件范围。

交付格式：
- 测试范围；
- 测试命令；
- 通过和失败情况；
- 问题复现步骤。

### Reviewer｜代码审查员

任务：
1. 独立检查 Git diff 和相关上下文。
2. 关注逻辑、安全、性能、兼容性和回归问题。
3. 按严重程度报告问题。
4. 默认只读，不直接修改被审查代码。

交付格式：
- 问题位置；
- 严重程度；
- 影响和复现条件；
- 修复建议；
- 审查范围及未覆盖事项。

## 五、标准执行步骤

### 第 1 步：检查项目

- 阅读项目根目录及相关目录的 `AGENTS.md`。
- 检查 Git 状态，保留用户已有修改。
- 阅读相关代码、配置、文档和测试。
- 明确目标、范围、约束和验收标准。

### 第 2 步：拆分任务

将任务拆成尽可能独立的工作项。每项都必须写明：

- 任务目标；
- 输入和依赖；
- 负责人；
- 只读或写入权限；
- 预期交付物；
- 验收标准。

### 第 3 步：并行执行

优先并行：
- 项目探索；
- 技术资料研究；
- 架构方案分析；
- 测试用例设计；
- 只读代码审查。

谨慎并行代码修改。为每个可写文件或文件组指定唯一负责人。不要让多个 Agent 同时修改同一文件。

### 第 4 步：整合与开发

- 主 Agent 汇总各角色的真实结果。
- 处理接口、数据结构和方案冲突。
- 由指定 Developer 或主 Agent 完成代码整合。
- 检查不同 Agent 的工作区是否隔离。
- 不假设不同 Cloud 任务共享文件系统、分支或未提交修改。
- 不覆盖用户已有修改。

### 第 5 步：测试和审查

- 从项目配置中识别真实测试和构建命令。
- 执行与本次改动相关的测试。
- 有条件时执行独立 Reviewer 审查。
- 修复确认的问题并重新测试。
- 未实际执行的测试不能标记为通过。

### 第 6 步：交付报告

使用中文输出：

1. 完成情况；
2. 实际 Agent 分工及状态；
3. 修改文件和主要内容；
4. 实际执行的测试及结果；
5. 未解决问题、风险和限制；
6. 后续建议。

如果没有创建原生子 Agent，必须明确写明“本次未创建原生子 Agent”，并说明是单 Agent 分阶段执行，还是仅生成了供用户另行启动的 Cloud 任务。

## 六、手动模式任务模板

用户指定角色时，按以下格式整理并执行：

```text
任务名称：<任务名称>
模式：MANUAL
并发上限：<数量>

Agent A：<角色>
职责：<明确任务>
权限：只读 / 可写指定文件
交付物：<结果格式>

Agent B：<角色>
职责：<明确任务>
权限：只读 / 可写指定文件
交付物：<结果格式>

依赖关系：<哪些任务必须等待其他任务>
验收标准：<可验证的完成条件>

主 Agent：负责协调、整合、测试、审查和最终交付。
```

## 七、独立 Cloud 任务交接模板

仅当当前环境不支持原生 Subagents，而用户仍希望使用多个 Cloud 任务时使用：

```text
这是一个独立协作任务，不要假设你能访问其他 Cloud 任务的工作区。

项目：<项目名称或仓库>
任务角色：<Explorer / Architect / Developer / Tester / Reviewer>
任务目标：<具体目标>
工作范围：<允许检查或修改的文件/模块>
禁止范围：<不得修改的文件/模块>
输入资料：<分支、提交、文档或用户提供的结果>
交付物：<报告、补丁、提交或测试结果>
验收标准：<明确条件>

请报告实际完成的工作，不要声称完成未执行的步骤。
```

## 八、安全要求

- 不输出或提交密钥、密码、访问令牌和私钥。
- 不擅自部署生产环境。
- 不未经确认执行破坏性删除、覆盖或不可逆迁移。
- 不修改生产数据库或权限配置，除非用户明确授权。
- 不覆盖用户已有的未提交修改。
- 不执行与任务无关的批量重构。
- 对高风险命令先解释影响并取得确认。

## 九、调用示例

### 自动模式

```text
请使用 multi-agent-dev 技能，MODE=AUTO。
先检查项目，再自动决定是否需要委派。若原生 Subagents 可用，最多并行启动 3 个；否则如实说明并按阶段完成。请实际实现、测试并交付。
```

### 手动模式

```text
请使用 multi-agent-dev 技能，MODE=MANUAL。
安排 Explorer、Architect、Developer、Reviewer 四个角色。
Explorer 和 Architect 只读并行；Developer 负责实现；Reviewer 在实现完成后独立审查。请明确文件写入边界和验收标准。
```

### 单 Agent 模式

```text
请使用 multi-agent-dev 技能，MODE=SINGLE。
不要创建子 Agent，由你独立完成需求分析、实施、测试和交付。
```
